Change the invoice schema.
Preserve the original close.

The signed invoice balance can hide unpaid exposure by netting credits. An opt-in dbt v2 contract separates gross unpaid amounts and credits while keeping every v1 column and value available.

Observed scope: synthetic fixtures executed locally on DuckDB 2.0.0 and a separate PostgreSQL 17.11 database. No cloud deployment, new Databricks result, stakeholder adoption or production savings is claimed.

What changed

Native dbt versions keep v1 as the default. Five validated physical snapshots feed stable consumer views, promoted together with the active-release pointer in one transaction. A multi-query reader pins an immutable release schema; it does not assume repeatable read freezes mutable view definitions.

Verified behavior

  • Each adapter passed 14 migration checks and four dbt builds; all 51 nodes passed in each build.
  • Complete incremental and full-refresh rows match an independent Python oracle and match between adapters.
  • A corrupted candidate and an interruption after the second view replacement preserve all previous stable views and the active pointer.
  • A second connection promotes after a reader pins its release. The reader still returns its original complete output.
  • Rollback restores canonical output bytes. A fresh warehouse rebuild from the frozen source reproduces the original close.
  • The existing nine-build, 39-check dbt regression also passes on both adapters; it is retained coverage, not a new capability.

Boundaries

One writer; workflow-frozen snapshots, not protection against a database administrator. Controlled exception recovery is not a process-kill or power-loss benchmark. Multi-query clients must pin a release schema. A knowledge cutoff alone cannot reconstruct a source snapshot after delayed deliveries. Version 1 is retained; no real consumer sign-off or retirement is invented.
